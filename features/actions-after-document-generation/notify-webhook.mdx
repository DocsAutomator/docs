The Notify Webhook feature allows DocsAutomator to send notifications to external services when documents are successfully generated. This enables integration with other applications and workflows.

## Purpose

Notify other services about successful document creations through webhook callbacks, allowing you to trigger downstream processes or log document generation events in external systems.

## Configuration

### Webhook URL Registration

Register a webhook address that will receive notifications once documents are created. DocsAutomator makes POST requests to your specified endpoint when generation completes.

<Steps>
  <Step title="Open the Actions card">
    In the automation editor, open the **Actions** card in the right rail and click **Add action**
  </Step>
  <Step title="Add the webhook action">
    Pick **Notify Webhook** from the action list
  </Step>
  <Step title="Enter URL">
    Enter your webhook endpoint URL
  </Step>
  <Step title="Test">
    Click **Send test event**, or generate a preview document
  </Step>
</Steps>

## Headers and Body Format

In **Send to**, choose **Any URL** to send to your own endpoint. You can add request headers, for example an API key. Turn on **Secret** for a header value that must stay private: DocsAutomator stores it encrypted, shows only its last 4 characters afterwards, and sends it only to the address it was saved for. After you change the webhook URL to another address, enter the secret again.

**Body format** sets the shape of the request body:

- **DocsAutomator JSON** (default): the event as shown below.
- **Text wrapped**: `{"text": "<the event as JSON>"}`.
- **Input wrapped**: `{"input": "<the event as JSON>"}`.

Click **Send test event** to send a sample signed event with the saved settings and see the answer code. To start a Claude routine or a ChatGPT agent, see [Start a Claude or ChatGPT Agent](/features/actions-after-document-generation/start-an-ai-agent).

## Additional Parameters via API

The system supports sending supplementary data alongside webhook notifications through the `webhookParams` object in API requests.

```json
{
  "docId": "your-automation-id",
  "data": {
    "customer_name": "Acme Corp"
  },
  "webhookParams": {
    "orderId": "ORD-12345",
    "customerId": "CUST-789"
  }
}
```

These parameters appear in the webhook payload sent to your endpoint under two keys with identical content: `webhookParams` (matching the request parameter name) and `additionalParams` (the original key, kept for backward compatibility). Use whichever you prefer — existing integrations built on `additionalParams` keep working unchanged.

## Webhook Payload Structure

```json
{
  "event": "document.created",
  "pdfUrl": "https://...",
  "googleDocUrl": "https://docs.google.com/document/d/...",
  "documentName": "Invoice #123",
  "status": "completed",
  "webhookParams": {
    "orderId": "ORD-12345",
    "customerId": "CUST-789",
    "recId": "recAbC123XyZ"
  },
  "additionalParams": {
    "orderId": "ORD-12345",
    "customerId": "CUST-789",
    "recId": "recAbC123XyZ"
  }
}
```

## Webhook Events

Every webhook names its event in the `event` field. Use it to tell the events apart, because one webhook URL receives all of them.

| Event | When it fires |
|-------|---------------|
| `document.created` | A document was generated. With [Approvals](/features/approvals) on, it fires after the approval. |
| `document.approval_rejected` | An approver rejected a held document. Nothing was delivered. |
| `esign.*` | Signing and acceptance events. See the [e-sign webhook events](/features/docsautomator-esign/docsautomator-esign-api-reference#webhook-events). |

The `document.created` payload is shown above. A document released after an approval also carries an `approval` object.

The `document.approval_rejected` payload:

```json
{
  "event": "document.approval_rejected",
  "status": "approval_rejected",
  "logId": "unique-run-identifier",
  "documentName": "Invoice #123",
  "approval": {
    "status": "rejected",
    "rule": "all",
    "requestedAt": "ISO date string",
    "requestedBy": { "email": "jonas@example.com", "name": "Jonas Weber" },
    "decidedAt": "ISO date string",
    "decidedBy": { "email": "priya@example.com", "name": "Priya Nair", "forApprover": null },
    "reason": "Wrong amount, please check the quantity.",
    "approvers": [
      { "email": "priya@example.com", "name": "Priya Nair", "decision": "rejected", "decidedAt": "ISO date string" }
    ]
  }
}
```

## Trigger Record Identifier

<Info>
The identifier of the record that triggered the generation is included automatically, so you can match webhook notifications to records in your data source:

- **Airtable, SmartSuite, Notion**: `recId` (Notion `pageId` and button triggers are normalized to `recId`)
- **ClickUp**: `taskId`
- **Google Sheets**: `rowNumber` — positional at trigger time, so treat it as "which row triggered this" rather than a durable key

Your own `webhookParams` keys are never overwritten by the automatic identifier.
</Info>
